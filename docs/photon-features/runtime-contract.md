# Photon Feature Runtime, F0

This is a foundation checkpoint, not the completed runtime. Application interfaces here are our design. Public SDK declarations and compile-only probes are the API authority. Feature schemas do not implement messaging operations.

## One shared host

The target path is iMessage ↔ Photon cloud ↔ one persistent host. The host owns one Spectrum client lifecycle, Photon credentials, ingress and one SQLite database/production outbox. Features receive resource, media, stream, clock, transaction and claim services through `ExecutionServices`; they never construct a client, subscribe to ingress or hold independent provider credentials. `HostComposition` orders client startup, recovery, outbox startup and ingress; failed startup cleans up and readiness remains false. Activation defaults to disabled in the protocol fixture; installation must explicitly configure it.

Fresh installation uses a local SQLite file, WAL, synchronous FULL, busy timeout 5 seconds and user_version 1. No network filesystem or multi-host database access is supported. WT-08 must create a private 0700 host directory before SQLite/socket activation and protect database, WAL, SHM and credentials under that directory. A process lock/supervisor must guarantee one host; the F0 composition object prevents repeated starts on that object but does not yet implement a system-wide lock. Database setup must finish before ingress or outbox activation.

## Three distinct integration boundaries

1. Inbound transport is explicitly `photon-stream` or `photon-webhook`, implemented by WT-02. Persist typed event identity and scope before acknowledging upstream. Deduplicate by source/account/line/event identity, not message text. Retain edits/receipts using their own identity/version. Missing order/version remains absent; arrival order is not authoritative. Unknown payloads enter unresolved storage, never guessed actions.
2. Outbound provider is cloud iMessage via the single host-owned SDK client. The developer machine being a Mac does not select local iMessage. Before dispatch, WT-01 resolves authenticated context, all resource references and capability availability, then durably records a fenced attempt.
3. Wake is an injected `WakeAdapter`/`ExistingGrokTaskHandoff` pointing at a persisted handoff ID, existing task ID and generation. It is only a notification. A failed or duplicate wake cannot lose durable work or authorize an operation. The existing Grok orchestrator delegates substantive work to existing workers; no new model/router/Grok API or polling loop is introduced.

The bot retrieves work after waking via the implemented local `work.list` → `work.claim` route. Claim returns persisted typed events from the inbox. Heartbeat extends the lease; `work.ack` durably records acknowledgement. Handoff creation is a WT-02/WT-01 transaction requirement: inbox reduction, derived state and handoff row commit together, then wake after commit. Ack means the existing task accepted responsibility, not that messaging completed. The handoff adapter must make task acceptance idempotent by handoff ID before ack. Deployment-specific wake binding remains unknown.

The documented Spectrum webhook callback is fire-and-forget after the HTTP response. WT-02 must verify a public durable-before-ack ingress seam or document/resolve this loss window before selecting webhook ingress. Do not assume awaiting that callback delays upstream acknowledgement. Stream replay/catch-up guarantees also need an exact-version probe.

## Local trust boundary and wire protocol

`listenLocal` binds only a Unix-domain socket, never TCP. Caller-supplied directory must be owner-owned and mode 0700, socket mode 0600; existing paths are refused. It uses a host-configured random credential (at least 32 bytes entropy, represented by 64 hexadecimal characters) mapped to an authenticated principal. Credentials are transported in a local frame outside action JSON; comparisons use constant-time equality. No credential is generated from a context ID. One bounded UTF-8 JSON frame, followed by newline, is processed per connection; limit 262144 bytes including credential, timeout 5 seconds. The response is one JSON line, then close. WT-08's executable must read a 0600 credential file without putting credentials in command arguments or logs.

Frame: `{ "token": "<local secret>", "request": { "version": 1, "method": "work.list", "contextId": "...", "limit": 20 } }`. Supported routes: submit, status, capabilities, diagnostics, work.list, work.claim, work.heartbeat, work.ack, request.cancel. Work-management routes are not members of the 44-operation messaging registry. `LocalProtocol.dispatch` accepts an already authenticated principal argument only from the socket authenticator or an equally trusted caller. It validates context identity/principal binding, time, revocation and operation permission; the injected resolver must load current authoritative generation/authorization on every request. Submission/status/cancellation ownership checks remain the WT-01 `SubmissionPort` implementation, not an F0 guarantee.

Unix permissions isolate OS users. Processes sharing an OS account can read secrets, inspect memory or invoke this protocol as another process. The OS account is therefore one trust domain; credentials distinguish cooperative task principals but do not isolate hostile same-user processes. Stronger worker isolation needs distinct OS accounts/containers and brokered credentials. Parent directories must be administrator-controlled; the current implementation does not pin directory file descriptors against rename races. Root/admin access is outside this boundary. Never expose this socket through a public proxy.

A `contextId` is an opaque lookup key, not a bearer credential. Context records bind principal, project, provider, account, line, space, task, current generation, permissions, issued/expiry timestamps and revocation. Workers receive only explicitly scoped grants. Creating a new space still uses an authenticated account/line context; returned resources carry the actual new conversation scope and require a new scoped context before subsequent use. Never reuse the originating space scope for a newly created conversation.

## Durable execution rules for WT-01

The state package implements synchronous SQLite transactions, schema migration and revision CAS. `StateTables` types define durable context grants, task generation/cancellation, staged-media manifests, registered-stream metadata, inbox, unresolved events, task handoffs, outbox, attempts, multipart children, message/resource references, polls/votes, cards/sessions and recovery checkpoints. It is a storage primitive, not a completed durable executor. Rows use host-derived globally unique IDs. Outbox identity must hash principal + full scope + task + generation + idempotencyKey; canonical argument digest must include contract version/operation/arguments. Reusing that identity with different arguments is IDEMPOTENCY_CONFLICT. No provider call occurs inside a transaction.

Insert revision 0. Every update increments revision exactly once and matches previous revision plus immutable scope. Claims carry owner, expiry, monotonically increasing fence and task generation. Heartbeat does not grant a new fence. Reclaim after expiry grants a new fence. Check claim validity, current context revocation/generation and cancellation immediately before dispatch and before writing results/checkpoints; stale actors cannot commit results. Fences protect the database, not a provider already executing an HTTP call.

A pre-dispatch cancellation can become cancelled; after dispatch starts, interruption may leave unknown-outcome. Do not claim cancellation undid a provider side effect. Store each multipart child with stable index/key and receipt references; advance recovery checkpoint atomically with child completion. Prepared-but-never-dispatched work is retryable. A crash between provider acceptance and persistence is unknown-outcome unless a verified public provider idempotency or outcome-lookup seam resolves it. No automatic resend on uncertainty. The generic recovery documentation's clientGuid example is not evidence that this installed Spectrum send method accepts it. No advanced extension is approved at F0.

Receipts are separate observations. Queued, executor-completed, provider-accepted, observed-delivered, observed-read, blocked, failed, cancelled and unknown-outcome are distinct. Successful void calls return `value: {type: 'void'}` with an empty references array. A resolved SDK promise may be an unsupported warn-and-skip; it alone cannot prove acceptance/delivery. Late receipts must correlate account/line/space/provider message identity, with monotonic evidence handling and no replay of side effects. Capability evidence never upgrades itself from a schema fixture.

## Shared resource services

`ContextResolver` owns current policy lookup and operation authorization. `ResourceResolver` must verify persisted reference kind, parent identity, owner, scope and generation before returning SDK Space/Message objects. References in JSON are claims to resolve, not authority. `MediaStager` permits only host-registered staged bytes or scoped attachment references, validates declared digest/size/MIME against bytes, imposes 25 MiB limits, rejects symlinks/path escapes and enforces fetch egress/redirect/IP rules for provider attachment retrieval. Raw caller filesystem paths and arbitrary media URLs are absent from the schema. Rich-link/card URLs still require host egress policy before any SDK fetch. Registered templates and custom codecs must be allowlisted; a codec ID alone cannot authorize arbitrary payloads. `RegisteredStreams` verifies scope, generation, expiry and cancellation and returns an existing stream; it never evaluates code in JSON.

Fixed clocks, controlled crash hooks and a temporary real SQLite fixture exist under tests only. No fake provider, fixture or test module is selected as a production fallback. The registry rejects test-mode modules and incomplete production handler sets. Test files are excluded from package exports/files. This is an accidental-use boundary, not protection against a developer deliberately relabelling code.
